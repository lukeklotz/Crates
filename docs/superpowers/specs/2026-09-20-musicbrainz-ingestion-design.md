# MusicBrainz ingestion pipeline — design (in progress)

**Status:** Design complete. All open items resolved as of 2026-09-23 — see "Resolved decisions" below. Ready for implementation planning.

## Purpose

Phase 2 of the Crate project plan (`docs/crate-ml-engineering-project-plan.md`) needs a reproducible pipeline that turns MusicBrainz data into Crate's normalized album catalog. This replaces the small hand-written seed catalog (141 albums, `backend/src/crate_backend/scripts/seed_catalog.py`) built during Phase 1, which only has title/artist/year and no genre/tag/credit data. Phase 3 (non-ML baselines: genre-overlap, tag-overlap, graph features from shared musicians/producers/labels/instruments/artist relationships) and Phase 4 (TF-IDF text documents from genres/tags/credits/instruments/labels/text) both depend on this richer metadata existing.

## Decisions made

### Catalog scope
- **All genres**, not restricted to any single genre (an earlier jazz-only scoping was superseded once the goal was clarified as "search/recommend all types of music").
- **Release types:** primary type = Album; secondary type = none (studio) or Live. Compilations, Soundtracks, Remixes, and other secondary types are excluded (pre-LP-era compilation handling and other edge cases are deferred).
- **Target size:** bounded at roughly **10,000–25,000 albums**, matching the original Phase 2 plan and its stated philosophy ("begin with a modest catalog and single-machine processing, then expand... only when those additions solve a demonstrated problem"). A full-database import (well over a million release-groups) was explicitly rejected for now — it would pull Phase 8's scaling work forward without a demonstrated need.
- **Ranking/cap heuristic** (for when the genre+type filter yields more than the target count, which it will): require a minimum bar — at least one genre or tag present on the release-group itself — to exclude near-empty stub entries, then rank the remainder by tag-vote count and cap at the target. This has to run entirely on release-group-level data because the candidate set is fixed by the filter pass *before* the artist pass resolves anything (see pipeline architecture below) — an artist-relationship requirement isn't evaluable yet at that point. (Distinct-release-count as an additional notability signal — well-known albums get reissued/repressed more — was dropped from the heuristic along with the `release` dump; tag-vote count alone is the notability proxy for v1.) Known bias to carry forward honestly: this still skews toward genres/regions where MusicBrainz's volunteer tagging community is most active (Western rock/pop/electronic).
- **Existing seed data:** the 141-album generic seed catalog gets replaced once the MusicBrainz-derived catalog is ingested (not kept side by side — recommendation signal quality would be too uneven between hand-seeded rows with no metadata and fully-ingested rows).

### Acquisition mechanism
- **MusicBrainz JSON Data Dumps**, not the live rate-limited (1 req/sec) JSON API, and not a full local MusicBrainz Postgres mirror (`musicbrainz-docker`).
  - Rejected the live API for bulk loading: at full multi-genre scale (potentially hundreds of thousands of candidate release-groups before capping), sequential 1 req/sec calls would take weeks to months. The live API remains a good fit later for *incremental*, on-demand lookups (e.g. a user searches for an album not yet in the catalog).
  - Rejected a full Postgres mirror: heavier than needed (their full production schema, Docker Compose replication setup) when the JSON dumps already contain everything we need in the same shape as the live API's JSON responses.
- **Source:** `https://data.metabrainz.org/pub/musicbrainz/data/json-dumps` (mirrored at `ftp.musicbrainz.org`). One `.tar.xz` per entity type, containing an `mbdump/<entity>` file with one JSON object per line, in the same field shape the live web service returns. Data is CC0-licensed (public domain) per MusicBrainz's own dump documentation.
- **Dump files needed:** `release-group`, `artist`, `label`, `recording`.
  - **`release` is explicitly out of scope.** We do not need per-release tracklists, medium/track ordering, or release-level label/catalog-number data for v1 — album identity, credits, and relationships are resolved without it (see pipeline architecture below). This also means there is no "best representative release" selection step and no release-level label linkage; a label's association with an album, if captured at all, would have to come through a relationship embedded elsewhere (not currently planned for v1).
  - `recording` is needed *because* `release` is skipped: it's the only source of recording-level relationship data (performer/producer/engineer credits) for recordings that show up as artist-level relations. In practice most of that same credit data is already embedded directly on the `artist` record's own `relations[]` (see below), so `recording` is mainly a secondary enrichment source, not a required join.
  - **Skip** `work`, `event`, `series`, `url` — not needed for the relationship allowlist we're targeting.
- **Verified structural facts** (from MusicBrainz's own JSON Data Dumps documentation, cross-checked against a real dump pull on 2026-09-23):
  - Dumped records already embed genres, tags, aliases, annotations, ratings, and *most* relationships — equivalent to a maximal `inc=` live lookup. No follow-up API calls needed for the bulk build.
  - Confirmed empirically: an `artist` record's `relations[]` can carry direct artist→recording edges (e.g. `performer`, `producer`) with the target recording's id/title/length embedded inline, and artist→artist edges (e.g. `member of band`). This is the primary source of recording-level credit data now that `release` is skipped — no join through `release` is needed to get a credit relationship between an artist and a specific recording.
  - Work-linked relationships live only in the `work` dump (irrelevant, we're not using Work-level data for v1).
  - Monthly **sample dumps** exist (same paths, `sample` instead of `fullexport`) — useful for developing/testing the parsing pipeline before running it against the full multi-GB dumps.

### Pipeline architecture

**Scope correction (2026-09-23):** per-album performer/producer/instrument credits are **not achievable for v1**. That data lives on `artist.relations[]` as artist→recording edges, but there is no join from a recording back to a specific release-group without the `release` dump (recording → release → release-group). An artist's relation to a recording is real, but which *album in our catalog* that recording belongs to is unknowable without `release`. Confirmed with the project owner: proceed without `release` for v1; Phase 3's "shared musicians/producers between albums" graph feature is deferred until `release` is reconsidered (genre-overlap, tag-overlap, and an artist-to-artist relationship graph still ship). This also means `recording.tar.xz` and `instrument.tar.xz` are not consumed by the v1 pipeline — validated as part of the data-quality review, but nothing in the ingestion script reads them.

Two stages, run as a script analogous to the existing seed script (`uv run python -m crate_backend.scripts.ingest_musicbrainz`), idempotent so re-runs are safe:

1. **Filter pass** over the `release-group` dump (streamed line by line): keep entries matching the genre+type criteria above, holding their MBIDs + core metadata (title, `first-release-date`, `artist-credit`, `genres`, `tags`) in memory as the candidate set. No `release` join — release-group-level data is the album record as-is.
2. **Artist pass** over the `artist` dump (streamed): for every unique artist MBID encountered in step 1's `artist-credit`, resolve the artist's identity fields (name, sort-name, type, country) and filter `relations[]` down to the artist-to-artist allowlist (`member of band`, `collaboration`) to build a general artist relationship graph. Deduplicated by artist MBID so a heavily-featured artist is only resolved once. Artist→recording relations are read but discarded (no album to attach them to — see scope correction above).
3. **Cover art** (separate, live network calls — no bulk dump exists for this): `GET https://coverartarchive.org/release-group/{mbid}/front` per ingested album. A 404 means no art and is treated as `null`, not an error. Concrete pacing policy: 1 request/second (matching MusicBrainz's own documented API rate), exponential backoff starting at 1s and doubling to a 60s cap on 429/5xx responses, up to 5 retries before giving up and recording `cover_art_url = null`.

**Explicitly out of scope for v1 without `release`:** per-album tracklists, track ordering, medium/format data, release-level label/catalog-number, and per-album performer/producer/instrument credits. If any of these become needed later, that's a reason to add `release` back in.

Each stage is a separate function. The dump stages (about 10–15 minutes) write in a single transaction, so an interrupted run leaves the database unchanged and is simply re-run. The cover art stage (hours) commits as it goes and only checks albums that still have no `cover_art_url`, so it resumes where it stopped.

## Resolved decisions (2026-09-23)

1. **Relationship-type allowlist:** artist-to-artist only — `member of band`, `collaboration`. Performer/producer/engineer/instrument types are dropped from the allowlist entirely (no per-album credit table exists to attach them to — see scope correction above).
2. **Genre vs. tag:** separate tables, not a unified table with a flag — `genre` is MusicBrainz's curated, fixed vocabulary and `tag` is freeform folksonomy with volunteer vote counts; keeping them distinct keeps that provenance visible. No minimum vote-count threshold for v1 — every genre/tag present on a candidate release-group is imported with its MusicBrainz `count` as a weight column, so filtering/thresholding can happen at query time instead of at ingestion time (reversible; a hard floor at ingestion is not).
3. **Schema:** `Genre` (id, name) and `Tag` (id, name) lookup tables; `AlbumGenre`/`AlbumTag` join tables (album_id, genre_id/tag_id, count); `ArtistRelationship` graph-edge table (artist_id, related_artist_id, relationship_type), always stored in MusicBrainz's forward orientation (subject → object, e.g. member → band) so an edge read from both artists' records is one row rather than two. No `Credit` table and no `Label` table for v1 — both are out of scope per the corrections above.
4. **Testing/validation** (Phase 2 step 9): reuse the same checks already run against the raw dumps during the data-quality review — zero malformed lines, zero duplicate MBIDs, zero missing MBID/title, a credited artist missing from the artist dump is not a pipeline failure — the album still links to an `Artist` row built from the credit's own embedded MBID and name, which just has no relationships — invalid `first-release-date` strings are stored as `null` rather than guessed at, and names longer than their column are clipped rather than aborting the run. Coverage stats (% with genre, % with tag, % with any artist relation) are logged at the end of each ingestion run.
5. **Provenance:** the ingestion script logs the source dump's `TIMESTAMP`/`SCHEMA_SEQUENCE`/`REPLICATION_SEQUENCE` (already extracted once for the data-quality review) at the start of each run; no new database table for this in v1 — run logs are sufficient provenance for a single-operator pipeline, and a table can be added later if multiple ingestion runs need to be compared programmatically. Cover Art Archive images are user-uploaded and not CC0 like the MusicBrainz dump data; v1 stores only `cover_art_url` with no per-image license field, since Crate doesn't yet display attribution UI that would need it — revisit if/when that UI exists.
6. **Cover Art Archive rate limiting:** see pipeline architecture stage 3 above — 1 req/s, exponential backoff (1s → 60s cap), 5 retries.
7. **Label linkage:** confirmed unresolved without `release` — `label.tar.xz` stays downloaded and validated (for whenever `release` is reconsidered) but is not read by the v1 ingestion script.
